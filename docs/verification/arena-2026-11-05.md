## Acceptance audit

| Requirement | Implementation and evidence |
| --- | --- |
| Allocation/reclamation API | `TupleArena` owns immutable typed tuple payloads in stable slot objects. Intrusive live/free lists support allocation, erase and clear without tombstone traversal. Reclaimed slots retain metadata and release values/strings. Arena payload storage is used by every `ReferenceTable`, including the support runtime's working copies; no alternate unused storage prototype is substituted. |
| Stable generational handles | `ArenaHandle` contains distinct owner, slot and uint64 generation. Free-slot reuse advances generation only after successful tuple copy; exhausted generations never wrap/reenter the free list. Same-owner erased/wrong-generation/malformed handles are absent for contains/erase, and get/pin throw `stale_handle` in Debug and Release. Foreign owners reject. Public logical `TupleHandle` IDs remain monotonic and unchanged. |
| Noncopyable ownership and exact strings | Arena and pin owners are noncopyable with guarded noexcept moves. Tuples retain exact layout tokens and owned strings/typed int64/bool/date/decimal values. No dictionary or borrowed string lifetime is introduced. A 128-KiB string and address stability through 2,048 further allocations pass. |
| Defined pinned retention | Move-only pins preserve immutable payload/address after erase, clear, owner destruction or replacement. Membership/indexes disappear immediately; retired pinned slots cannot be reused. Multiple pins count independently and the last release reclaims the value. Owner destruction clears unpinned payloads; pinned values and high-water metadata remain until final release. Pins do not preserve cursors or create runtime epochs. |
| Independent churn model | Luna Max's three fixed seeds exercise 650 operations each: 1,950 arena states. Expected slot liveness/generation/value/pin counts are tracked independently and every historical handle and all arena statistics are checked after each operation. The reference-table model performs 5,600 operations over eight seeds, independently checks set/index/pin state and exact peak slot metadata, then releases all payloads. |
| Reference integration | Tests cover duplicate/absent identity behavior, indexed/nullary bulk deletion, live cursor invalidation, multiple pins, slot reuse without logical ID aliasing, clear, table destruction and move replacement. Plan-storage copies have fresh table/arena owners and independent payloads, preserve logical ID/index counters, and omit retired records/pins/high-water metadata. Existing independent S02 and R01–R03 models remain in the matrix. |
| Failed allocation consistency | Separate global-allocation sweeps fail every position before first success: four fresh-slot, two reused-slot, four vector-growth and 18 indexed-table insert positions. Arena failures preserve all published statistics, prior generations, values, handles, pin addresses and free/live-list consistency; retry succeeds. Table failures preserve rows/indexes/public IDs/revision/live/retained/pin counts and borrowed/pinned addresses; free high-water metadata may grow. Successful pin creation/release, arena erase and clear are also checked with allocations disabled. |
| Support regression | The support failure sweeps now cover 185 last-child insertion, 199 supported-child deletion and 101 final-candidate reclamation positions, preserving complete state/sequence/public handles with retry. Full working-copy transaction costs remain explicit; S03 does not complete R04 or claim output-sensitive updates. The older storage sweeps now cover 15 insert, 61 index build, 50 bulk erase and two tuple-assignment positions. |

## Limits and continuation

Generation exhaustion and owner/pin counter exhaustion are guarded in code;
tests do not traverse the uint64/size_t range. Models exercise finite seeds,
not exhaustive state spaces. `check_invariants` allocates temporary visited
arrays and scans all slots. Pointer-vector growth and final metadata
destruction cost O(slots); clear visits only current live records. The arena
is a reusable reference pool, with individual stable slot allocations and
high-water metadata retention, not an optimized allocator.

Statistics count records/slots/pins, not allocator bytes or reserved vector
capacity. A pin can retain all slot metadata after owner destruction. S04/S05
must address optimized indexes, capacity budgets and full memory accounting.
Pins supply payload lifetime only. R04 still needs affected-record journal
entries and allocation-safe undo that preserves row IDs/generations; ordinary
reinsert allocates a new logical ID and is not an undo operation. Full
working-copy support updates, R05 physical alias epochs, cursors/deltas,
recovery and release review retain their acceptance criteria.
